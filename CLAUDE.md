# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ResumePress started as a resume builder and was merged with a job-application tracker (Applications, Contacts, Interactions, Gmail sync — see "Job Application Tracker" below) across `PLAN.md`'s phases 0-4, all now complete. `PLAN.md` (original spec) and `docs/MIGRATION_PLAN.md` (the actual decisions made, with their rationale) are the detailed historical record of *why* things are the way they are; this file documents *what exists now* and should be kept current as the living reference — treat a stale section here as a bug.

## Commands

```bash
npm run dev          # Start dev server (localhost:3000)
npm run build        # Production build
npx tsc --noEmit     # Type-check without building

npm run db:migrate   # Run Prisma migrations (requires running Postgres)
npm run db:seed      # Seed built-in categories
npm run db:studio    # Open Prisma Studio

# Add a shadcn component (uses base-ui variant, NOT Radix)
npx shadcn@latest add <component-name>
```

Postgres must be running for `dev` and `db:*` commands. `.env` (see `.env.example`) needs `DATABASE_URL=postgresql://postgres:postgres@localhost:5432/resumepress?schema=public`, plus `AUTH_SECRET` (generate with `npx auth secret`), `AUTH_GOOGLE_ID`, and `AUTH_GOOGLE_SECRET` from a Google Cloud OAuth 2.0 Web application client (authorized redirect URI: `<origin>/api/auth/callback/google`, for both `http://localhost:3000` and the Sevalla production domain), plus `ALLOWED_EMAILS` and `GMAIL_TOKEN_ENCRYPTION_KEY` (see "Auth" below), and `TYPESAFE_API_KEY` (see "AI Features (Jev)" below).

## Architecture

**Stack:** Next.js 16 App Router · TypeScript · Tailwind CSS v4 · Prisma 5 + PostgreSQL · shadcn/ui (base-ui variant)

**PDF generation:** `GET /api/pdf/[resumeId]` fetches the resume + selected entries from the DB and groups them by category, then hands off to `compileResumeToPdf` (`src/lib/resumeCompiler.ts`, see "Key Patterns"), which renders via `src/templates/jake.ts`, writes the `.tex` to a temp dir, runs `pdflatex` twice, and returns the PDF buffer for the route to stream back. `GET /api/pdf/snapshot/[snapshotId]` is the counterpart for a frozen `ResumeSnapshot` (see "Resume version history" below) — same `compileResumeToPdf` call, but sourced from the snapshot's own inlined entry content via `snapshotSectionsToEntriesByCategory` (`src/lib/resumes.ts`) instead of a live Prisma fetch. The same `compileResumeToPdf` is also called by the MCP `compile_resume` tool (see "MCP Server") for DB-free, inline compiles. pdflatex must be installed locally (`brew install --cask mactex-no-gui`) or is included in the Docker image via `apt-get install texlive-*`.

**Deployment:** Docker + Sevalla. `docker-entrypoint.sh` runs `prisma migrate deploy`, seeds categories, then `node server.js`. `next.config.ts` uses `output: "standalone"`.

**Auth:** two independent auth systems, for two different kinds of client.

- **Browser/session auth** — NextAuth.js (Auth.js v5) with Google OAuth only, configured in `src/lib/auth.ts` (database session strategy via `@auth/prisma-adapter`). **App-wide allowlist**: every page under `src/app/(protected)/` (which is every page except `/login` and `/unauthorized`) is gated by `src/app/(protected)/layout.tsx`, which redirects to `/login` with no session, or `/unauthorized` if the session's email isn't in `ALLOWED_EMAILS` (comma-separated — more than one person can use a deployment, each with fully isolated `userId`-scoped data). Route Handlers (`route.ts`) aren't covered by layouts, so each one that needs the gate checks it explicitly — see `GET /api/pdf/[resumeId]`'s use of `getAllowedUserId()`. (This is additive to, not a replacement for, the `userId`-scoped ownership-check pattern below — see docs/MIGRATION_PLAN.md §1.2. It also pairs with, rather than replaces, restricting the Google Cloud OAuth consent screen's own Test users list, which blocks anyone not on it before they ever reach this app.) Helpers from `src/lib/auth.ts`:
  - `getUserId()` — for pages/reads. Returns the session's user id or `null`; never redirects. Now effectively always non-null on a gated page (the layout guarantees a session), but still null-checked defensively — kept as a fail-safe, not removed, when the gate was added.
  - `requireUserId()` — for server actions that write data. Redirects to `/login` if there's no session.
  - `isAllowedEmail(email)` — the allowlist check itself (membership in `ALLOWED_EMAILS`, case-insensitive).
  - `getAllowedUserId()` — for Route Handlers only; returns the caller's `userId` or `null` (no session, or not on the allowlist).
- **Agent/API-key auth** — a separate bearer-token mechanism in `src/lib/apiToken.ts`, purpose-built for non-browser clients (the MCP server below). `generateApiToken()` mints a `rp_`-prefixed random token and stores only its SHA-256 hash; `getUserIdFromBearerToken(req)` reads the `Authorization: Bearer <token>` header, hashes it, looks up the `ApiToken` row, checks `revokedAt`/`expiresAt`, bumps `lastUsedAt`, and returns the associated `userId` (or `null`). Users create/revoke tokens at `/settings/tokens` (session-authenticated page, uses `requireUserId()`). This system never touches NextAuth sessions or cookies, and is **not** covered by the allowlist gate above — it's a separate authorization boundary, scoped per-token rather than per-session, and `/api/mcp` must stay reachable without a browser session for the Claude connector to work.
- **Gmail connection** (optional, independent of login) — `src/lib/encryption.ts` (AES-256-GCM, keyed by `GMAIL_TOKEN_ENCRYPTION_KEY`, separate from `AUTH_SECRET`) and `src/lib/gmailAccount.ts` back a `GmailAccount` row per user. `/api/gmail/oauth/{start,callback}` run their own OAuth handshake against the *same* `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` client (just a second authorized redirect URI + the `gmail.readonly` scope) — deliberately not through NextAuth's `signIn()`/`Account`, so re-consenting for Gmail never fights the adapter's own token-write path. Managed at `/email` (connection + sync settings share that page with the triage queue — see "Gmail sync" below). See docs/MIGRATION_PLAN.md §1.1 for why this is a separate table/flow instead of reusing `Account`. The actual sync/matching logic built on top of this connection is covered in "Job Application Tracker" below, not here — this section is just the OAuth/token-storage half.

## MCP Server

`src/app/api/mcp/route.ts` exposes ResumePress over the Model Context Protocol (`@modelcontextprotocol/sdk`) so agents (e.g. a Claude.ai custom connector) can work with a user's data via a bearer token instead of a browser session. The `POST` handler authenticates via `getUserIdFromBearerToken`, builds a per-request `McpServer`, and calls `registerResumePressTools(server, userId)` (`src/lib/mcpTools.ts`) before handing the request to the SDK's streamable-HTTP transport. `registerResumePressTools` keeps the original 8 resume-builder tools inline and delegates everything else to one `register*Tools(server, userId)` function per domain under `src/lib/mcp/` (`entryTools.ts`, `resumeTools.ts`, `applicationTools.ts`, `contactTools.ts`, `interactionTools.ts`, `emailTools.ts`, `searchTools.ts`) — mirroring the app's own lib-file-per-module split. `src/lib/mcp/shared.ts` holds the `textResult`/`errorResult` content-block helpers every tool uses.

**Full parity with the front end is the goal**, with two deliberate exceptions:
- `/settings/tokens` (mint/revoke `ApiToken`s) has no MCP tool — letting a bearer-token-authenticated call mint or revoke bearer tokens is a credential-escalation surface, not app data, so it's excluded on purpose.
- Gmail **connect** has no tool — it's a browser OAuth redirect (`/api/gmail/oauth/start`) that can't run over a stateless bearer-token call. Disconnect, sync, and triage all do have tools, since those are just data operations on the already-connected account.

Tools are scoped to the authenticated `userId` and roughly mirror each module's own actions.ts, with one structural difference: MCP tools call the underlying `*ForUser` lib functions directly rather than importing actions.ts, because actions.ts functions call `redirect()`/`notFound()`/`revalidatePath()` — Next.js request-lifecycle APIs that don't make sense (and in the case of `redirect()`, actively break the response) outside a page request. Where this left logic duplicated between an action and its MCP tool (e.g. the applications list's bulk status-change/delete), it was pulled into a shared `*ForUser` function in the lib file instead, so the action and the tool both call one implementation (see `bulkUpdateApplicationStatusForUser`/`bulkDeleteApplicationsForUser` in `applications.ts`).

Tool groups, all scoped to the authenticated `userId`:
- **Resume builder** (original 8, inline in `mcpTools.ts`) — `list_categories`, `list_entries`, `get_entry`, `create_entry`, `list_resumes`, `get_resume`, `create_resume`, and `compile_resume`, the one tool that **never touches Prisma**: it takes identity + entries fully inline (no DB ids) and templateId, compiles a PDF via `compileResumeToPdf` (`src/lib/resumeCompiler.ts`), and returns the PDF as a base64 `resource`/`blob` content block in the same response — a stateless "compile and discard" path, validated against `compileResumeSchema` (`src/lib/schemas/resumeEntry.ts`); an unrecognized `templateId` is a hard validation error here (unlike the DB-backed PDF route, which silently falls back to `jake`).
- **`entryTools.ts`** — `update_entry`, `delete_entry`, `clone_entry`, `list_entry_versions`, `create_category`, `delete_category`.
- **`resumeTools.ts`** — `update_resume_identity`, `update_resume_entries`, `duplicate_resume`, `delete_resume`.
- **`applicationTools.ts`** — companies (`list_companies`, `get_company`) and applications (`list_applications`, `get_application`, `create_application`, `update_application`, `update_application_status`, `log_application_update`, `set_application_history_note`, `delete_application_status_history_entry`, `delete_application`, `bulk_update_application_status`, `bulk_delete_applications`, `get_application_pipeline_stats`, `get_application_status_flow`, `attach_resume_to_application`, `detach_resume_from_application`, `import_applications`). `import_applications` takes already-mapped rows (the shape the CSV/Notion importer UI produces post-column-mapping) — the CSV parsing/column-guessing step itself is pure UI convenience with no server-side analog worth exposing.
- **`contactTools.ts`** — `list_contacts`, `get_contact`, `create_contact`, `update_contact`, `delete_contact`, `link_contact_to_application`, `unlink_contact_from_application`.
- **`interactionTools.ts`** — `log_interaction`, `delete_interaction` (mirrors the "ignore the linked email thread" side effect from `contacts/actions.ts`'s `deleteInteraction`).
- **`emailTools.ts`** — `get_gmail_connection_status`, `sync_gmail_now`, `disconnect_gmail`, `get_email_sync_stats`, `list_triage_threads`, `list_ignored_threads`, `confirm_email_thread_match`, `ignore_email_thread_match`, `restore_email_thread_match`, `bulk_confirm_email_thread_matches`, `bulk_ignore_email_thread_matches`, `create_contact_from_triage`, `create_application_from_triage`. See "Gmail sync" below for what's proven (the deterministic sync/matching mechanics, exercised in production) versus newer and not yet similarly proven (eager Jev classification, the full-inbox scan, the transient full-body fetch) — a `sync_gmail_now` call made by an agent exercises all of it.
- **`searchTools.ts`** — `search` (wraps `globalSearch`).

Tool input schemas are defined with zod directly alongside each tool (mostly ad hoc per tool, matching the original style); `compile_resume`'s schema lives separately in `src/lib/schemas/resumeEntry.ts`. Mutating tools that accept freeform strings (notes, summaries, etc.) cap their lengths the same way `entryCoreFieldsSchema`/`compileResumeSchema` do, since every one of these paths bypasses whatever length limits the corresponding form UI enforces (added in the Phase 4 audit for the original tools — see "Job Application Tracker" below — and applied the same way to every tool added since).

## Job Application Tracker

A companies/applications/contacts/interactions/Gmail-sync tracker merged into this app across `PLAN.md`'s phases 0-4 (all complete). Every table below is additive to the original resume-builder schema and follows the same `userId`-scoped ownership-check pattern (see "Key Patterns").

**Applications** (`src/lib/applications.ts` + `applicationsShared.ts`, `src/app/(protected)/applications/**`) — a list/kanban CRUD for `Application`, grouped under a `Company` (found-or-created by free-text name via `findOrCreateCompanyForUser` in `src/lib/companies.ts`). Every status change writes an `ApplicationStatusHistory` row in the same transaction; `APPLICATION_STATUSES` (`applicationsShared.ts`) is a 6-value suggested list (Applied/OA/Interviewing/Offer/Rejected/Ghosted, default "Applied") — a UI affordance, not a DB constraint, trimmed from a longer original list per GitHub issue #17. History entries can also carry a freeform `note` (editable after the fact, or added via a note-only "log update" with no status change) instead of inventing more statuses. The kanban board (`ApplicationsKanban.tsx`) hides empty status columns except while a card is being dragged, and also offers a per-card `<select>` as a keyboard-operable alternative to drag-and-drop. `ResumeSection` on the detail page is a resume picker (attach/open/recompile-PDF/change/remove) backed by its own `resumeActions.ts`, kept separate from this module's own `actions.ts` by original design (two independently-built pieces touching the same file). A column-mapping CSV importer lives at `/applications/import` (`src/lib/csv.ts` + `src/lib/notionImportShared.ts`) for migrating from an external tracker (e.g. Notion) whose export columns won't match any fixed format — mapping a column to `Application.externalId` makes re-imports idempotent. (An earlier fixed-format CSV export/import pair existed and was removed as dead code once issue #17 unwired it from the UI with no replacement home ever built — don't resurrect that shape; the column-mapping importer is the one to extend if more import sources are needed.)

**Contacts & Interactions** (`src/lib/contacts.ts` + `interactions.ts` + `interactionsShared.ts`, `src/app/(protected)/contacts/**`) — contacts exist independently of any application (`Application`/`Contact` are linked many-to-many via `ApplicationContact`, which carries a free-form `role`). `Interaction.contactId`/`applicationId` are both nullable and independent — an interaction can belong to either, both, or (if its contact/application is later deleted — `onDelete: SetNull`) neither. Both the application and contact detail pages render the same `InteractionTimeline`/`LogInteractionForm`/`ApplicationLinks`-or-`ContactLinks` components from whichever side's module they conceptually belong to (contacts); don't duplicate them per-side. A global "Log interaction" quick-add (`GlobalQuickAdd.tsx`, floating button + the `i` keyboard shortcut) is mounted in `src/app/(protected)/layout.tsx` — deliberately the protected layout and not the root layout, so it only renders for an authenticated, allowlisted session and never shows on `/login`.

**Gmail sync** (`src/lib/gmail.ts` + `emailThreads.ts`, unified at `/email`) — read-only (`gmail.readonly` only; grep `src/lib/gmail.ts` for any write/send/modify call before ever adding one — there should be none). `/email` (`src/app/(protected)/email/page.tsx`) combines Gmail connection/sync settings and the triage queue into one page: a connection card (`GmailConnectionPanel.tsx`: connect/disconnect, "Sync now", collapsed by default), a "Needs review" list (`TriageList`, unmatched threads only), and a collapsible ignored-threads list below it. Uses plain `fetch` against the Gmail REST API, not the `googleapis` package, matching the OAuth routes' own style.

"Sync now" scans the inbox — read and unread, regardless of label (`listInboxThreadIds` in `gmail.ts`, paginated) — replacing an earlier label-picker + History-API-incremental design (`GmailAccount.syncLabelIds`/`historyId` are left in the schema, unused, rather than dropped — a destructive migration for no benefit). Capped at `INBOX_SCAN_LIMIT` (1000) most recently active threads per sync (Gmail's list endpoint returns newest-first, so this means "the 1000 most recent," not an arbitrary truncation) and re-scanned fresh each time rather than tracked incrementally — unlike "currently unread," the full inbox only grows, so that cap is the only thing bounding cost on a large or long-lived inbox. **Matching is two-tiered by design**: an exact participant-email-to-contact match auto-links (`matchStatus: "auto"`); a company-domain-to-application guess is only ever a *suggestion*, never auto-linked — anything not exactly contact-matched lands in the "Needs review" list (`matchStatus: "unmatched"`) for manual confirm/reassign/ignore. In that list, once a contact is picked for a thread, the application `<select>` narrows to just the applications that contact is actually linked to via `ApplicationContact` (`listApplicationIdsByContactForUser` in `contacts.ts`), falling back to the full list when the contact has none — see `TriageList.tsx`'s `visibleApplicationOptions`. When a contact *is* matched, the application link isn't just the domain guess: `loadMatchCandidates()` also builds an `applicationByContact` map straight from `ApplicationContact` (an explicit link the user made, not a guess) and prefers it — a matched contact's email thread "pushes through" onto whichever application that contact is actually linked to (most-recently-updated one, if linked to several), landing directly on that application's interaction timeline. Every sync also re-runs matching against all currently-`"unmatched"` threads using already-stored data (no Gmail call) — without this, a contact added after a thread's first sync would never retroactively match, since a thread that's aged out of the 1000-most-recent scan window would otherwise never be looked at again. The same re-run also backfills the application link on already-`"auto"`/`"confirmed"` threads that matched a contact but got no application at the time — covers a contact being linked to an application *after* their email already synced. It also demotes any `"auto"`/`"confirmed"` thread back to `"unmatched"` if it has lost *both* its contact and application link (e.g. the matched `Contact` or `Application` was deleted — both FKs are `onDelete: SetNull`) — otherwise that thread would be stuck invisible forever, since it's neither `"unmatched"` (shows in Needs review) nor `"ignored"` (shows in the ignored list). Deleting a Gmail-sourced `Interaction` (one with an `emailThreadId`) also sets its `EmailThread` to `matchStatus: "ignored"` rather than leaving a dangling `"auto"` match with no visible trace; the ignored-threads list has a Restore action as the undo path. A confirmed/auto match mirrors itself onto the matched contact's/application's interaction timeline (idempotent across resyncs — checks for an existing `Interaction` with that `emailThreadId` first); that timeline (`InteractionTimeline.tsx`) renders an "Open email" link straight to Gmail for any interaction with an `emailThread.gmailUrl`, and a `Contact`'s own `emails[]` render as `mailto:` links on its detail page.

**Eager Jev triage classification** — for threads the deterministic pass above leaves `"unmatched"`, `classifyThreadForTriage` (`emailThreads.ts`) asks Jev, in one combined call, whether the thread is recruiting-related (`noul`) and which existing contact/application it's most likely about (`choice`, same shape as the on-demand "Suggest match" button below). This is the one deliberate exception to every other Jev feature's on-demand-only, bounded-cost design (see "AI Features (Jev)" below) — classification only re-runs for a thread when its content is new or changed since the last pass (`jevClassifiedAt` vs `lastMessageAt`), not on every sync click, to keep the eager cost bounded to actual new activity. Recruiting-related but matching nothing tracked yet escalates to a "new opportunity" guess: a company name deterministically from the sender's non-webmail-domain address, and a role title from Jev disambiguating between subject-line segments (never generated — same actionability principle as `jobPosting.ts`). A thread that already has a resolved application (an exact match, or a Jev guess from a prior pass) instead gets a status-change question scoped to that thread's own content — e.g. a rejection email for an application still marked "Applied" surfaces as a dismissible "Jev suggests marking this application Rejected" prompt in the triage row, with Apply calling the same `updateApplicationStatus` the application detail page's own status control uses. The full message body is fetched transiently (`getThreadBodyText`) for this classification only and never persisted — `EmailThread` continues to store only subject/snippet, same as before. `TriageList.tsx` renders all of this as a prefilled pick (Confirm/Ignore are still required, same as a manual pick) rather than requiring the on-demand "Suggest match" button first.

The deterministic sync/matching mechanics above have been exercised against a real Gmail account in production use and are reasonably proven; the eager classification, full-inbox scan, and transient full-body fetch are newer and have not yet seen the same real-world mileage — treat their suggestions with proportionally more skepticism until they have.

**Automatic (cron-triggered) sync** — `POST /api/cron/gmail-sync` (`src/app/api/cron/gmail-sync/route.ts`) runs the same `syncGmailForUser` as the manual "Sync now" button, but loops every connected account (`listAllGmailAccountUserIds()` in `gmailAccount.ts`) instead of just the signed-in user, so it can be fired on a schedule with no browser session involved. It isn't gated by `ALLOWED_EMAILS`/NextAuth (there's no session to check) — it's its own authorization boundary, a single shared secret: the request must carry `Authorization: Bearer <CRON_SECRET>`, checked with a length-matched `timingSafeEqual` and failing closed (401) if `CRON_SECRET` is unset, same spirit as the `ApiToken` bearer scheme in "Auth" above but app-wide instead of per-user. One account's sync failing (expired refresh token, no labels configured, Gmail API error) is caught per-account and reported in the JSON response rather than aborting the rest of the batch. The trigger itself lives outside this repo: a Sevalla `cron` process (same Docker image/app, different process type — see docs/MIGRATION_PLAN.md §3) on a schedule, running something like `curl -fsS -X POST -H "Authorization: Bearer $CRON_SECRET" https://<domain>/api/cron/gmail-sync`, configured in the Sevalla dashboard/API, not in this repo's code. `CRON_SECRET` must be set in both `.env` (local, if testing the route) and Sevalla's environment variables for the deployed app.

**Dashboard & search** — the home page (`src/app/(protected)/page.tsx`) surfaces the 5 most recently updated applications (via `listApplicationsForUser(userId)`, sliced to 5) and a pending-triage count. The contacts-due-for-follow-up section (`Contact.nextFollowUpAt`, via `listContactsForUser(userId, { followUpDue: true })`) it originally shipped with was swapped out for this; that query/helper and the `/contacts?followUp=due` route it linked to still exist and work, just aren't surfaced from the dashboard anymore. `src/lib/search.ts` + `/search` is a case-insensitive `contains` search across `Application`/`Contact`/`Interaction`, surfaced via a plain GET-form search box in `Nav.tsx` (no client JS needed).

## AI Features (Jev)

`src/lib/jev.ts` is a thin, dependency-free client (plain `fetch`, no `@typesafe-ai/sdk` — matches `gmail.ts`'s own hand-rolled-REST-client convention) for [Jev](https://docs.typesafe.ai), TypeSafe AI's "System One" model. Jev has no free-text-generation primitive — `askJev(state, questions)` sends a `state` blob plus one or more typed questions (`choice`: pick from a fixed list; `score`: rate against an ordered rubric; `noul`: yes/no probability) to `POST https://api.typesafe.ai/v1/systemone` and gets back structured, probabilistic answers, never generated prose. Requires `TYPESAFE_API_KEY` (see "Commands" above); `askJev` returns `{ok:false, error}` rather than throwing when the key is missing or the request fails. **Every Jev-derived feature in this app is a suggestion the user explicitly confirms — nothing is ever auto-applied on Jev's output, regardless of confidence** (an earlier ATS-bullet-scoring feature was built, then reverted, because a bare score with no actionable next step is the wrong use of a non-generative model; only build Jev features whose output feeds directly into an action the UI already has).

Built so far, suggestion-only throughout — one deliberate exception runs automatically instead of on a user click:
- **Eager triage classification** (`classifyThreadForTriage` in `emailThreads.ts`, surfaced in `TriageList.tsx`) — runs automatically during Gmail sync rather than on a user click, the one exception to every other Jev feature here; see "Gmail sync" above for the full design (what it classifies, how the eager cost is bounded, the full-body-fetched-but-never-persisted detail) and why it was accepted specifically here.
- **"Suggest match" button** (`src/components/gmail/TriageList.tsx` + `suggestMatchForThreadForUser` in `emailThreads.ts`) — one Jev call with two Choice questions (contact, application) evaluated against the same triage-thread `state`, prefilling the row's contact/application pickers exactly as a manual pick would; Confirm/Ignore are unaffected.
- **"Suggest status" chip** (`src/components/applications/SuggestStatusButton.tsx` + `suggestApplicationStatusForUser` in `applications.ts`) — a Choice question over `APPLICATION_STATUSES` against an application's most recent Gmail-sourced interactions, surfaced next to `EditableStatusBadge` with an explicit Apply step that calls the same `updateApplicationStatusForUser` a manual status change uses.
- **"Autofill from link"** (`ApplicationForm.tsx` + `extractJobPostingFromUrl` in `src/lib/jobPosting.ts`) — given a job-posting URL, fills the new/edit Application form's company/role/location/term fields, never submitting. Mostly deterministic, not Jev-driven: it prefers a `schema.org JobPosting` JSON-LD block (most job boards embed one) and only falls back to a Jev Choice question when JSON-LD is missing and regex-found candidates (`<title>`, `og:title`, `og:site_name`, first `<h1>`) are ambiguous — Jev always picks one of those candidates verbatim, never generates a value. Fetching an arbitrary external URL server-side is new territory for this codebase (everything else hits a fixed, known host) — `src/lib/urlFetch.ts` is the SSRF-guarded fetcher behind it: rejects non-http(s) schemes, resolves and rejects private/loopback/link-local IPs (including after each redirect hop, followed manually to avoid a validate-then-redirect bypass), times out (~10s), and caps response size (~2MB). Only fills currently-empty fields — never overwrites something the user already typed.

## Key Patterns

**Server Actions** are the mutation layer — every create/update/delete is a `"use server"` function in an `actions.ts` file colocated with its route. Pages are async RSC that fetch directly via `prisma`; all data-fetching pages export `dynamic = "force-dynamic"`.

**Ownership checks:** `Entry`, `Resume`, custom `Category`, and every tracker model (`Company`/`Application`/`Contact`/`Interaction`/`ApplicationContact`/`EmailThread`) have a required/nullable `userId`. Prisma's singular `update`/`delete`/`findUnique` build their `where` from unique fields only — adding `userId` alongside `id` there does **not** enforce ownership. Always use `updateMany`/`deleteMany` with `{ id, userId }` in `where` and check the returned `count` (0 means not found or not owned → `notFound()`), and use `findFirst` (not `findUnique`) with `{ id, userId }` for ownership-checked reads. Built-in categories have `userId: null`; category lookups that should include them use `where: { OR: [{ userId: null }, { userId }] }`. **The one legitimate exception** is `GmailAccount`, whose `userId` field is itself `@unique` (one row per user) — `findUnique`/`update` keyed on `userId` alone is correct there, not a bypass, because `userId` *is* the unique key, not a secondary filter alongside a different one. Don't generalize that exception to any other model. A Phase 4 audit found one real ownership-check miss in `confirmEmailThreadMatchForUser` (a caller-supplied `contactId`/`applicationId` was written without verifying it belonged to the caller) — if you're touching anything that accepts a foreign id from client input, check that it's actually owned by `userId` before using it, not just the row being updated.

**Client-safe shared modules:** when a client component needs a server module's pure constants/types/CSV-or-matching logic (e.g. `APPLICATION_STATUSES`, a status-history formatter), split that pure logic into its own `*Shared.ts` file with **no runtime import of `@/lib/prisma`** (only `import type` from `@prisma/client`, which is erased at compile time) — see `applicationsShared.ts`, `interactionsShared.ts`, `notionImportShared.ts`. Importing the Prisma-touching lib file directly from a client component bundles the Prisma client into client-side JS. The `*.ts` file (no `Shared`) stays server-only and re-exports its `*Shared.ts` counterpart (`export * from "./xShared"`) so server code can import everything from one place.

**shadcn/ui here uses `@base-ui/react`**, not Radix UI. Important differences:
- `Button` has no `asChild` prop — use `buttonVariants` on a `<Link>` instead: `<Link className={cn(buttonVariants({ variant: "outline" }))}>`
- `Select.Value` renders the raw value string, not the selected item's label — render the label manually in the trigger
- `Checkbox` renders as `<button>`, not `<input>` — native `<label>` won't forward clicks to it; use a `<div onClick>` with `pointer-events-none` on the Checkbox
- `AlertDialog` does not use a Trigger in this codebase — manage `open` state manually

**Rich text in bullets/descriptions** is stored as plain strings with `**bold**` and `*italic*` markers. `applyFormatting()` in `src/templates/jake.ts` converts these to `\textbf{}` / `\textit{}` after LaTeX-escaping. The preview parses them to `<strong>` / `<em>` in `EntryForm.tsx`.

**Entry field visibility** is driven by `src/lib/entryFields.ts`. `FIELD_CONFIGS` maps category slugs to `FieldConfig` objects that control which fields render in `EntryForm`. Add a new built-in category type by adding an entry to `FIELD_CONFIGS`; custom categories fall back to `DEFAULT_FIELD_CONFIG` (all fields).

**PDF compilation** is centralized in `src/lib/resumeCompiler.ts`'s `compileResumeToPdf(templateId, identity, entriesByCategory)` — the pdflatex/tempdir/cleanup mechanics (write `.tex`, run `pdflatex` twice with a timeout, read the PDF, clean up in `finally`) live here exactly once. `GET /api/pdf/[resumeId]` (DB-backed, session-authenticated), `GET /api/pdf/snapshot/[snapshotId]` (frozen-snapshot-backed), and the MCP `compile_resume` tool (inline data, bearer-token-authenticated) all call this same function — each just builds `EntriesByCategory` differently (live Prisma fetch, snapshot JSON, or inline request data) before handing off. Any future template-selection or pdflatex-invocation change belongs here, not duplicated in a route.

**Resume version history** (GitHub issue #26) addresses two gaps: `Entry` had no edit history, and `ResumeEntry` is a *live* FK to `Entry`, so editing an Entry retroactively changed every `Resume` (and every `Application`) referencing it — there was no way to pin "the resume as it was when I applied."
- **Entry history** — `updateEntryForUser` (`src/lib/entries.ts`) snapshots an Entry's pre-update field values into `EntryVersion.data` (a JSON blob) before applying an edit, skipping the write entirely when the edit is a no-op (deep-equal old/new). It's audit-log only by design — no revert button; reverting means copying old values back into the form by hand. `EntryHistory.tsx` renders the list (collapsed by default) on the entry edit page, each row expandable to show that version's full field dump.
- **Resume pinning** — attaching a resume to an application (`attachResumeToApplication`, `src/app/(protected)/applications/resumeActions.ts`) calls `createResumeSnapshotForUser` (`src/lib/resumes.ts`), which freezes the resume's *current* rendered content (identity + each entry's content inlined, grouped by category exactly like the PDF route groups it) into a new `ResumeSnapshot`, and points `Application.resumeSnapshotId` at it. `Application.resumeId` is kept too, but only for UI navigation (the "Open"/"Change" resume picker in `ResumeSection.tsx` still deals with the live `Resume`) — the snapshot, not the live resume, is what the application is actually pinned to, and what "Download PDF" compiles from. Later edits to the resume's entries never change an already-attached application. There's no automatic re-sync: "Refresh snapshot" in `ResumeSection.tsx` re-runs the same attach flow against the already-attached resume to deliberately pull in edits by creating a fresh snapshot. Applications attached before this feature shipped have `resumeSnapshotId: null` and fall back to compiling the live resume until re-attached.

**LaTeX template** lives entirely in `src/templates/jake.ts`. `escapeLatex` → `applyFormatting` → template string. Education uses `\resumeSubheading{school}{location}{degree}{date}` (location is arg #2, date is arg #4) — this differs from Experience where date is arg #2.

**Do not edit the static LaTeX in `jake.ts`** (the preamble, custom commands like `\resumeItem`/`\resumeSubheading`, margins, `\titleformat`) without a deliberate decision to diverge from upstream. The template must stay byte-for-byte identical to the canonical upstream template (https://github.com/jakegut/resume/blob/master/resume.tex — the "Jake Ryan" resume, credited in `jake.ts`'s own header comment) except for one documented, necessary exception:

- `\usepackage[T1]{fontenc}` + `\usepackage[utf8]{inputenc}` — added in commit `ac0dc83` (2026-09-06). Upstream doesn't need these because it's a static example with hardcoded ASCII sample text; ResumePress renders arbitrary user-entered Unicode (accented names like "José", "Renée"). Verified by direct testing: without these packages, modern pdfTeX doesn't crash, but accented characters render/extract as decomposed glyphs (e.g. "í" → "ı" + floating accent mark) — a real, visible defect, not just cosmetic. This is the one deviation from upstream; everything else (margins, custom commands, section layout) matches exactly.

Run `npm run check:jake-template` after any change to `jake.ts` — it renders the template with fixed dummy data and diffs the output against the golden fixture at `src/templates/__fixtures__/jake.golden.tex`, failing loudly (with a line-level diff) on any unintended change. If a change to the static LaTeX is genuinely needed, update the golden fixture *and* add the new discrepancy to the list above in the same commit — don't let the two drift apart.

**Card spacing gotcha:** The shadcn Card applies `py-(--card-spacing)` (16px) to itself plus `gap-(--card-spacing)` between children. For list-row cards that use `CardContent` with its own `py-*`, add `py-0` to the `Card` to avoid double-stacking vertical padding.

## Data Model


`identity` JSON shape: `{ name, email, phone, website, linkedin, github }`.

Built-in category slugs: `experience`, `education`, `projects`, `skills`. These slugs are matched in `renderSection()` in `jake.ts` to determine which LaTeX render function to call.

## Adding a New Template

1. Create `src/templates/<name>.ts` exporting a `render(identity, entriesByCategory)` function with the same signature as `jake.ts`.
2. Register it in `TEMPLATE_RENDERERS` in `src/lib/resumeCompiler.ts`.
3. Add it to the `TEMPLATES` array in `src/app/(protected)/resumes/new/page.tsx`.
