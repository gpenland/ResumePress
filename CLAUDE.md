# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ResumePress started as a resume builder and was merged with a job-application tracker (Applications, Contacts, Interactions, Gmail sync — see "Job Application Tracker") across `PLAN.md`'s phases 0-4, all complete. `PLAN.md` (original spec) and `docs/MIGRATION_PLAN.md` (decisions made, with rationale) are the historical record of *why*; this file documents *what exists now* and should be kept current — treat a stale section here as a bug.

## Commands

```bash
npm run dev          # Start dev server (localhost:3000)
npm run build        # Production build
npx tsc --noEmit     # Type-check without building

npm run db:migrate   # Run Prisma migrations (requires running Postgres)
npm run db:seed      # Seed built-in categories
npm run db:studio    # Open Prisma Studio

# Add a shadcn component (uses base-ui variant, NOT Radix)
npx shadcn@latest add <component-name>
```

Postgres must be running for `dev` and `db:*` commands. `.env` (see `.env.example`) needs `DATABASE_URL=postgresql://postgres:postgres@localhost:5432/resumepress?schema=public`, `AUTH_SECRET` (`npx auth secret`), `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` (Google Cloud OAuth 2.0 Web client; authorized redirect URI `<origin>/api/auth/callback/google` for both `http://localhost:3000` and the Sevalla production domain), `ALLOWED_EMAILS` and `GMAIL_TOKEN_ENCRYPTION_KEY` (see "Auth"), `TYPESAFE_API_KEY` (see "AI Features (Jev)"), and `CRON_SECRET` (see "Automatic sync"; also set in Sevalla's env).

## Architecture

**Stack:** Next.js 16 App Router · TypeScript · Tailwind CSS v4 · Prisma 5 + PostgreSQL · shadcn/ui (base-ui variant)

**PDF generation:** `GET /api/pdf/[resumeId]` fetches the resume + selected entries, groups them by category, and hands off to `compileResumeToPdf` (`src/lib/resumeCompiler.ts`, see "Key Patterns"), which renders via `src/templates/jake.ts`, runs `pdflatex` twice in a temp dir, and returns the PDF buffer. `GET /api/pdf/snapshot/[snapshotId]` does the same for a frozen `ResumeSnapshot` (see "Resume version history"), sourcing entries from the snapshot's inlined content via `snapshotSectionsToEntriesByCategory` (`src/lib/resumes.ts`). The MCP `compile_resume` tool also calls `compileResumeToPdf` for DB-free inline compiles. pdflatex must be installed locally (`brew install --cask mactex-no-gui`); the Docker image gets it via `apt-get install texlive-*`.

**Deployment:** Docker + Sevalla. `docker-entrypoint.sh` runs `prisma migrate deploy`, seeds categories, then `node server.js`. `next.config.ts` uses `output: "standalone"`.

**Auth:** two independent systems for two kinds of client.

- **Browser/session auth** — NextAuth.js (Auth.js v5), Google OAuth only, in `src/lib/auth.ts` (database sessions via `@auth/prisma-adapter`). **App-wide allowlist**: every page under `src/app/(protected)/` (all pages except `/login` and `/unauthorized`) is gated by `src/app/(protected)/layout.tsx`, which redirects to `/login` with no session, or `/unauthorized` if the email isn't in `ALLOWED_EMAILS` (comma-separated; multiple people can use one deployment, each with fully isolated `userId`-scoped data). Route Handlers aren't covered by layouts, so each checks explicitly (see `GET /api/pdf/[resumeId]`'s `getAllowedUserId()`). This is additive to the `userId`-scoped ownership-check pattern (docs/MIGRATION_PLAN.md §1.2) and pairs with restricting the Google Cloud consent screen's Test users. Helpers in `src/lib/auth.ts`:
  - `getUserId()` — pages/reads; session user id or `null`, never redirects. Effectively always non-null on a gated page but still null-checked as a fail-safe.
  - `requireUserId()` — server actions that write; redirects to `/login` without a session.
  - `isAllowedEmail(email)` — case-insensitive `ALLOWED_EMAILS` membership.
  - `getAllowedUserId()` — Route Handlers only; `userId` or `null` (no session, or not allowlisted).
- **Agent/API-key auth** — bearer tokens in `src/lib/apiToken.ts` for non-browser clients (the MCP server). `generateApiToken()` mints an `rp_`-prefixed token and stores only its SHA-256 hash; `getUserIdFromBearerToken(req)` hashes the `Authorization: Bearer` header, looks up the `ApiToken`, checks `revokedAt`/`expiresAt`, bumps `lastUsedAt`, and returns the `userId` (or `null`). Users manage tokens at `/settings/tokens` (session-authenticated, `requireUserId()`). Never touches NextAuth sessions/cookies and is **not** covered by the allowlist gate — a separate boundary scoped per-token; `/api/mcp` must stay reachable without a browser session for the Claude connector.
- **Gmail connection** (optional, independent of login) — `src/lib/encryption.ts` (AES-256-GCM keyed by `GMAIL_TOKEN_ENCRYPTION_KEY`, separate from `AUTH_SECRET`) and `src/lib/gmailAccount.ts` back a per-user `GmailAccount` row. `/api/gmail/oauth/{start,callback}` run their own OAuth handshake against the *same* `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` client (second redirect URI + `gmail.readonly` scope), deliberately not through NextAuth's `signIn()`/`Account` so re-consenting never fights the adapter's token writes (docs/MIGRATION_PLAN.md §1.1). Managed at `/email`. **Expired/revoked tokens**: `refreshAccessToken` throws `GmailAuthError` on `invalid_grant`/`invalid_client`/`unauthorized_client`; `syncGmailForUser` then sets `GmailAccount.needsReauth` and skips further syncs/cron attempts until cleared. Surfaced by a red banner in `(protected)/layout.tsx`, a dot on the Email nav tab, and a "Reconnect Gmail" button in `GmailConnectionPanel`. Reconnect re-runs `/api/gmail/oauth/start` against the *existing* row — `saveGmailAccount` keeps `lastSyncAt`/`syncLabelIds` (resetting only if the Google mailbox differs), so the next sync is incremental; "Disconnect" deletes the row and causes a full rescan. Frequent expiry's root cause: a Google Cloud consent screen in "Testing" caps refresh tokens at 7 days — publish to Production (unverified-app warning is fine for a single owner). Sync/matching logic is under "Job Application Tracker".

## MCP Server

`src/app/api/mcp/route.ts` exposes ResumePress over MCP (`@modelcontextprotocol/sdk`) so agents (e.g. a Claude.ai custom connector) can use a bearer token instead of a browser session. `POST` authenticates via `getUserIdFromBearerToken`, builds a per-request `McpServer`, calls `registerResumePressTools(server, userId)` (`src/lib/mcpTools.ts`), then hands off to the SDK's streamable-HTTP transport. `registerResumePressTools` keeps the original 8 resume-builder tools inline and delegates the rest to one `register*Tools(server, userId)` per domain under `src/lib/mcp/` (`entryTools`, `resumeTools`, `applicationTools`, `contactTools`, `interactionTools`, `emailTools`, `searchTools`). `src/lib/mcp/shared.ts` holds the `textResult`/`errorResult` helpers.

**Full parity with the front end is the goal**, with two deliberate exceptions:
- `/settings/tokens` (mint/revoke `ApiToken`s) has no tool — letting a bearer-authenticated call mint/revoke bearer tokens is a credential-escalation surface.
- Gmail **connect** has no tool — it's a browser OAuth redirect. Disconnect, sync, and triage do have tools.

Tools call the underlying `*ForUser` lib functions directly, not actions.ts, because actions call `redirect()`/`notFound()`/`revalidatePath()`, which don't work (`redirect()` actively breaks the response) outside a page request. Where logic would be duplicated between an action and its tool, it lives in a shared `*ForUser` function both call (e.g. `bulkUpdateApplicationStatusForUser`/`bulkDeleteApplicationsForUser` in `applications.ts`).

Tool groups (all scoped to the authenticated `userId`):
- **Resume builder** (inline in `mcpTools.ts`) — `list_categories`, `list_entries`, `get_entry`, `create_entry`, `list_resumes`, `get_resume`, `create_resume`, `compile_resume`. `compile_resume` **never touches Prisma**: it takes identity + entries + templateId inline, compiles via `compileResumeToPdf`, and returns the PDF as a base64 `resource`/`blob` block — stateless "compile and discard", validated by `compileResumeSchema` (`src/lib/schemas/resumeEntry.ts`). An unrecognized `templateId` is a hard validation error here (the DB-backed PDF route silently falls back to `jake`).
- **`entryTools.ts`** — `update_entry`, `delete_entry`, `clone_entry`, `list_entry_versions`, `create_category`, `delete_category`.
- **`resumeTools.ts`** — `update_resume_identity`, `update_resume_entries`, `duplicate_resume`, `delete_resume`.
- **`applicationTools.ts`** — `list_companies`, `get_company`, `list_applications`, `get_application`, `create_application`, `update_application`, `update_application_status`, `log_application_update`, `set_application_history_note`, `delete_application_status_history_entry`, `delete_application`, `bulk_update_application_status`, `bulk_delete_applications`, `get_application_pipeline_stats`, `get_application_status_flow`, `list_application_cycle_options`, `attach_resume_to_application`, `detach_resume_from_application`, `import_applications`. `import_applications` takes already-mapped rows (CSV parsing/column-guessing is UI-only). `list_applications`, `get_application_pipeline_stats`, and `get_application_status_flow` take an optional `cycles` array (see "Recruiting-cycle filter"); `list_application_cycle_options` mirrors the dropdown's option list.
- **`contactTools.ts`** — `list_contacts`, `get_contact`, `create_contact`, `update_contact`, `delete_contact`, `link_contact_to_application`, `unlink_contact_from_application`.
- **`interactionTools.ts`** — `log_interaction`, `delete_interaction` (mirrors `contacts/actions.ts`'s "ignore the linked email thread" side effect).
- **`emailTools.ts`** — `get_gmail_connection_status`, `list_gmail_labels`, `save_override_label`, `sync_gmail_now`, `cancel_stuck_sync`, `clear_unmatched_threads`, `disconnect_gmail`, `get_email_sync_stats`, `list_triage_threads`, `list_ignored_threads`, `confirm_email_thread_match`, `ignore_email_thread_match`, `restore_email_thread_match`, `bulk_confirm_email_thread_matches`, `bulk_ignore_email_thread_matches`, `list_email_status_suggestions`, `apply_email_status_suggestion`, `dismiss_email_status_suggestion`, `create_contact_from_triage`, `create_application_from_triage`. A `sync_gmail_now` call exercises everything under "Gmail sync", including the newer, less-proven parts.
- **`searchTools.ts`** — `search` (wraps `globalSearch`).

Input schemas are zod, defined alongside each tool (`compile_resume`'s lives in `src/lib/schemas/resumeEntry.ts`). Mutating tools that accept freeform strings cap their lengths like `entryCoreFieldsSchema`/`compileResumeSchema`, since MCP paths bypass the form UI's limits (added in the Phase 4 audit; apply to every new tool).

## Job Application Tracker

Companies/applications/contacts/interactions/Gmail-sync tables are additive to the resume-builder schema and follow the same `userId`-scoped ownership-check pattern (see "Key Patterns").

**Applications** (`src/lib/applications.ts` + `applicationsShared.ts`, `src/app/(protected)/applications/**`) — list/kanban CRUD for `Application`, grouped under a `Company` (found-or-created by free-text name via `findOrCreateCompanyForUser`, `src/lib/companies.ts`). Every status change writes an `ApplicationStatusHistory` row in the same transaction. `APPLICATION_STATUSES` is a 7-value suggested list (Applied/OA/Interviewing/Offer/Rejected/Ghosted/Withdrawn, default "Applied") — a UI affordance, not a DB constraint (trimmed per issue #17; Withdrawn added per #117). Withdrawn is treated like Rejected/Ghosted wherever status signals terminal/stale (dashboard "active" count, Gmail triage application picker's stale-status tie-breaker). History entries can carry a freeform, later-editable `note`, or be added as a note-only "log update" with no status change, instead of inventing more statuses. The kanban (`ApplicationsKanban.tsx`) hides empty status columns except while dragging and has a per-card `<select>` as a keyboard alternative to drag-and-drop. `ResumeSection` on the detail page is a resume picker (attach/open/recompile-PDF/change/remove) backed by `resumeActions.ts`, deliberately separate from `actions.ts`. A column-mapping CSV importer at `/applications/import` (`src/lib/csv.ts` + `src/lib/notionImportShared.ts`) migrates from external trackers (e.g. Notion); mapping a column to `Application.externalId` makes re-imports idempotent. An earlier fixed-format CSV export/import pair was removed as dead code — don't resurrect it; extend the column-mapping importer instead.

**Recruiting-cycle filter** (issue #106) — a "cycle" is Fall of year Y plus the following Spring/Summer, named by its Fall year (the "2026" cycle = Fall 2026 – Summer 2027). There's no `cycle` column: `src/lib/recruitingCycleShared.ts` derives it on read by regex-parsing `Application.term` for a season+year (`parseTermToCycle`, e.g. "Summer 27", "fall 2026"), falling back to `appliedAt` via `cycleForDate` when `term` is empty/unparseable (`cycleForApplication`). `cycleForDate` maps Jan–Apr to the *prior* year's cycle and May–Dec to the current year's (matching the issue's application window, ~June Y – April Y+1), which makes `currentCycle()` correct mid-summer (June 2026 → 2026 cycle). Filtering is in-memory, not Prisma `where`: `listApplicationsForUser`, `getApplicationPipelineStatsForUser`, and `getApplicationStatusFlowForUser` (via a two-step application-id lookup, since `ApplicationStatusHistory` has no `term`/`appliedAt`) take an optional `cycles: number[]`; `undefined` = all cycles. The UI default is the current cycle: `parseCycleSearchParam` resolves a missing `?cycle=` to `[currentCycle()]`, and only an explicit `?cycle=all` yields `undefined` (URL-only persistence). `listApplicationCycleOptionsForUser` builds the dropdown: every cycle present in the user's applications plus the current one even if empty, newest first. `CycleFilter.tsx` (multi-select on `DropdownMenuCheckboxItem`) is shared by the dashboard Statistics panel and the applications page, each defaulting independently.

**Contacts & Interactions** (`src/lib/contacts.ts` + `interactions.ts` + `interactionsShared.ts`, `src/app/(protected)/contacts/**`) — contacts exist independently of applications (many-to-many via `ApplicationContact`, which carries a free-form `role`). `Interaction.contactId`/`applicationId` are independently nullable — an interaction can belong to either, both, or (after the other side is deleted, `onDelete: SetNull`) neither. Application and contact detail pages share the same `InteractionTimeline`/`LogInteractionForm`/`ApplicationLinks`-or-`ContactLinks` components (from contacts); don't duplicate per side. A global "Log interaction" quick-add (`GlobalQuickAdd.tsx`, floating button + `i` shortcut) is mounted in the protected layout, not the root, so it never shows on `/login`.

**Gmail sync** (`src/lib/gmail.ts` + `emailThreads.ts`, unified at `/email`) — read-only (`gmail.readonly` only; grep `gmail.ts` for any write/send/modify call before ever adding one — there should be none). `/email` (`src/app/(protected)/email/page.tsx`) combines a collapsed-by-default connection card (`GmailConnectionPanel.tsx`: connect/disconnect, "Sync now"), a "Needs review" list (`TriageList`, unmatched threads only), and a collapsible ignored-threads list. Uses plain `fetch` against the Gmail REST API, not `googleapis`.

"Sync now" scans the inbox — read and unread, any label (`listInboxThreadIds`, paginated) — replacing an earlier label-picker + History-API design (`GmailAccount.syncLabelIds`/`historyId` stay in the schema rather than a destructive migration). The *first* sync (no `lastSyncAt`) scans the whole inbox, capped at `INBOX_SCAN_LIMIT` (1000) most recently active threads (Gmail lists newest-first). **Later syncs are incremental**, scoped by Gmail's `after:<timestamp>` operator anchored at `lastSyncAt` minus a 15-minute overlap buffer (a message arriving *during* a sync is dated before the run's completion timestamp, so an exact cutoff would miss it forever; re-covering a few threads is harmless — upserts are idempotent and classification skips unchanged ones). Without this, every resync cost the same quota as the first (~10 minutes for ~500 threads). `clearUnmatchedThreadsForUser` (the "Clear unmatched emails" debug control and `clear_unmatched_threads` tool) deletes unmatched `EmailThread` rows (never confirmed/ignored) to re-test from a clean slate, and also resets `lastSyncAt` to `null` so the resync isn't scoped to a narrow incremental window that would never re-fetch the deleted threads. The label-override scan (`listThreadIdsForLabel`) is `labelIds`-based, not date-based, so it's unaffected.

**Gmail API quota**: every `gmail.ts` call goes through `gmailFetch`, which (1) throttles call *starts* to one per `MIN_GMAIL_CALL_INTERVAL_MS` (250ms) **per account** — a concurrency cap alone doesn't bound calls per second once each completes quickly, and doesn't prevent bursting through Gmail's per-user "Total Query Cost / Units per minute" quota (hit in production as a 403 `rateLimitExceeded`, not 429). Keyed per ResumePress `userId` (not the rotating access token) because the quota is per Gmail account, so one user's sync never slows another's; and (2) retries rate-limited responses with exponential backoff up to a ~60s cumulative ceiling, long enough to outlast the per-*minute* window (the retry counter lives on the call stack, so needs no per-account keying). `getThreadDetails` fetches metadata and body in one `format=full` call (same quota as one `threads.get`, half the per-thread cost). `THREAD_SYNC_CONCURRENCY` (3) only bounds threads in flight, not call rate (the throttle owns that).

**Sync runs in the background**: a sync over hundreds of threads takes minutes, longer than a browser request (or reverse proxy) should be expected to survive. `startGmailSyncInBackgroundForUser` (`emailThreads.ts`) atomically claims a `GmailAccount.syncStatus` "running" slot (`markSyncRunningForUser` — prevents the cron job and a manual click from double-syncing) and returns immediately; the un-awaited `syncGmailForUser` keeps running because this is a long-lived Node process (Docker + `node server.js`), not serverless. Its optional `onProgress` writes `syncTotal`/`syncDone` to the same row. `GmailConnectionPanel.tsx` polls `getGmailSyncStatusForUser` every 1.5s while `syncStatus === "running"` (whoever started it — status lives in the DB, not component state) and calls `router.refresh()` once on the transition out of "running". A first-ever sync gets more reassuring copy ("this can take a few minutes... progress picks back up when you return"); later syncs show lighter wording. `runTrackedGmailSyncForUser` is the awaited counterpart (same slot guard, returns the final `SyncResult`), used by the cron route and MCP `sync_gmail_now`, which have no browser timeout.

**Stale "running" recovery**: nothing clears `syncStatus` if the process dies mid-sync (deploy, crash, restart), which would otherwise leave "Sync now" disabled forever (its `disabled` follows `syncStatus === "running"`). `isStale`/`STALE_SYNC_THRESHOLD_MS` (20 minutes) covers it two ways: `markSyncRunningForUser` lets a *new* sync reclaim a stale `"running"` row, and `getGmailSyncStatusForUser` detects staleness on read and persists a correction to `"error"` — needed because a disabled button would never let a reclaim attempt happen. A "Cancel" control next to the progress bar (`cancelSync` action → `cancelStuckSyncForUser`, MCP `cancel_stuck_sync`) avoids waiting out the window. Concurrency safety: `markSyncRunningForUser` returns the exact `syncStartedAt` it claimed, and every finalize path (`finalizeSyncStatus`, used by the background sync and `runTrackedGmailSyncForUser`) applies only via `updateMany({ where: { syncStartedAt: claimedAt } })` — otherwise a "dead" sync that finishes late could overwrite a cancellation or a newer sync's progress. `cancelStuckSyncForUser` sets `syncStartedAt` to `null` so any late zombie finalize fails that comparison.

**Matching is two-tiered**: an exact participant-email-to-contact match auto-links (`matchStatus: "auto"`); a company-domain-to-application guess is only ever a *suggestion* — anything not exactly contact-matched lands in "Needs review" (`"unmatched"`) for manual confirm/reassign/ignore. In that list, once a contact is picked, the application `<select>` narrows to applications that contact is linked to via `ApplicationContact` (`listApplicationIdsByContactForUser`), falling back to all when none (`TriageList.tsx`'s `visibleApplicationOptions`). When a contact *is* matched, `loadMatchCandidates()` builds an `applicationByContact` map straight from `ApplicationContact` (an explicit user link, not a guess) and prefers it — the thread lands on the contact's most-recently-updated linked application's timeline. Every sync also re-runs matching against all `"unmatched"` threads from stored data (no Gmail call), so a contact added later still matches a thread that has aged out of the 1000-thread scan window. That re-run also backfills the application link on `"auto"`/`"confirmed"` threads that matched a contact but got no application (contact linked to an application *after* the email synced), and demotes any `"auto"`/`"confirmed"` thread that lost *both* its contact and application (both FKs `onDelete: SetNull`) back to `"unmatched"` — otherwise it would be invisible forever, neither in Needs review nor ignored. Deleting a Gmail-sourced `Interaction` (one with `emailThreadId`) sets its `EmailThread` to `"ignored"` instead of leaving a dangling `"auto"` match; the ignored list has a Restore action as undo. A confirmed/auto match mirrors onto the contact's/application's timeline (idempotent — checks for an existing `Interaction` with that `emailThreadId`); `InteractionTimeline.tsx` renders an "Open email" link to Gmail for any interaction with `emailThread.gmailUrl`, and a `Contact`'s `emails[]` render as `mailto:` links.

**Eager Jev triage classification** — for threads left `"unmatched"`, `classifyThreadForTriage` (`emailThreads.ts`) asks Jev, in one combined call, whether the thread is recruiting-related (`noul`) and which existing contact/application it most likely concerns (`choice`, same shape as the on-demand "Suggest match"). This is the one deliberate exception to Jev features being on-demand-only (see "AI Features (Jev)"); cost is bounded because classification re-runs only when content is new or changed (`jevClassifiedAt` vs `lastMessageAt`), not on every sync. Recruiting-related but matching nothing tracked escalates to a "new opportunity" guess: company name deterministically from the sender's non-webmail domain, role title from Jev choosing among subject-line segments (never generated — same actionability principle as `jobPosting.ts`). A thread with a resolved application (exact match, or a prior Jev guess) instead gets a status-change question scoped to its own content — e.g. a rejection email for an application still "Applied" surfaces a dismissible "Jev suggests marking this application Rejected" prompt — in the triage row for an unmatched thread (applied to the row's current pick), or, for an already-matched (`"auto"`/`"confirmed"`) thread that never reaches the unmatched-only queue, in a "Suggested status updates" section atop `/email` (`StatusSuggestionsList.tsx` ← `listStatusSuggestionThreadsForUser`, which drops suggestions already matching the application's status or superseded by a status change after the thread's last message). Both go through `applyEmailThreadStatusSuggestionForUser`/`dismissEmailThreadStatusSuggestionForUser`: Apply uses the thread's stored `jevSuggestedStatus` (never a client-supplied value) via `updateApplicationStatusForUser`, then clears it; Dismiss just clears it — both persist across reloads, and a new message re-runs classification. The full message body is fetched transiently (`getThreadBodyText`) for classification only and never persisted — `EmailThread` stores only subject/snippet. `TriageList.tsx` renders all this as a prefilled pick; Confirm/Ignore are still required, same as a manual pick.

**The triage list is filtered by that classification**: `listTriageThreadsForUser` excludes unmatched threads Jev classified as not recruiting-related (`jevRecruitingLikely === false`), otherwise scanning the whole inbox would flood "Needs review" with newsletters/receipts. Written as an explicit `OR` over `true`/`null`/`labelForced` rather than `{ not: false }` to stay null-safe: unclassified threads (or those classified while Jev was down) must still show — the goal is hiding confirmed-irrelevant mail, not failing closed. **Manual override**: `GmailAccount.syncLabelIds` (repurposed) holds a Gmail label id set via `GmailConnectionPanel.tsx`'s "Always include a label" control; threads carrying it are pulled in via `listThreadIdsForLabel` regardless of the `INBOX_SCAN_LIMIT` window and marked `labelForced` (recomputed each sync, so removing the label un-forces it), which always wins over `jevRecruitingLikely` — the escape hatch for Jev mistakes or older threads.

The deterministic sync/matching mechanics have been exercised against a real Gmail account in production and are reasonably proven; eager classification, the full-inbox scan, and the transient full-body fetch are newer — treat their suggestions with proportionally more skepticism.

**Automatic (cron-triggered) sync** — `POST /api/cron/gmail-sync` (`src/app/api/cron/gmail-sync/route.ts`) runs `syncGmailForUser` for every connected account (`listAllGmailAccountUserIds()`) with no browser session. It isn't gated by `ALLOWED_EMAILS`/NextAuth; it's its own boundary, a shared secret: `Authorization: Bearer <CRON_SECRET>`, checked with length-matched `timingSafeEqual`, failing closed (401) if `CRON_SECRET` is unset. One account's failure (expired token, Gmail API error) is caught per-account and reported in the JSON response without aborting the batch. The trigger lives outside this repo: a Sevalla `cron` process (same image, different process type — docs/MIGRATION_PLAN.md §3) running e.g. `curl -fsS -X POST -H "Authorization: Bearer $CRON_SECRET" https://<domain>/api/cron/gmail-sync`, configured in the Sevalla dashboard/API.

**Dashboard & search** — the home page (`src/app/(protected)/page.tsx`) shows the 5 most recently updated applications (`listApplicationsForUser(userId)` sliced to 5) and a pending-triage count. The contacts-due-for-follow-up section it originally had was removed from the dashboard, but `Contact.nextFollowUpAt`, `listContactsForUser(userId, { followUpDue: true })`, and `/contacts?followUp=due` still exist and work. `src/lib/search.ts` + `/search` is a case-insensitive `contains` search across `Application`/`Contact`/`Interaction`, via a plain GET-form box in `Nav.tsx`.

## AI Features (Jev)

`src/lib/jev.ts` is a dependency-free client (plain `fetch`, no `@typesafe-ai/sdk`, matching `gmail.ts`'s style) for [Jev](https://docs.typesafe.ai), TypeSafe AI's "System One" model. Jev has no free-text generation: `askJev(state, questions)` sends a `state` blob plus typed questions (`choice`: pick from a fixed list; `score`: rate against an ordered rubric; `noul`: yes/no probability) to `POST https://api.typesafe.ai/v1/systemone` and returns structured, probabilistic answers. Requires `TYPESAFE_API_KEY`; returns `{ok:false, error}` rather than throwing when the key is missing or the request fails. **Every Jev-derived feature is a suggestion the user explicitly confirms — nothing is auto-applied on Jev's output, regardless of confidence.** An earlier ATS-bullet-scoring feature was built then reverted because a bare score with no actionable next step is the wrong use of a non-generative model; only build Jev features whose output feeds an action the UI already has.

Built so far (suggestion-only; one runs automatically):
- **Eager triage classification** (`classifyThreadForTriage`, `TriageList.tsx`) — runs during Gmail sync, the one exception to on-demand use; full design under "Gmail sync".
- **"Suggest match"** (`TriageList.tsx` + `suggestMatchForThreadForUser`) — one call, two Choice questions (contact, application) over the thread's `state`; prefills the row's pickers like a manual pick, Confirm/Ignore unaffected.
- **"Suggest status"** (`SuggestStatusButton.tsx` + `suggestApplicationStatusForUser`) — a Choice over `APPLICATION_STATUSES` against an application's most recent Gmail-sourced interactions, next to `EditableStatusBadge`, with an explicit Apply calling the same `updateApplicationStatusForUser` as a manual change.
- **"Autofill from link"** (`ApplicationForm.tsx` + `extractJobPostingFromUrl`, `src/lib/jobPosting.ts`) — fills the Application form's company/role/location/term from a job-posting URL, never submitting, and only fills currently-empty fields. Mostly deterministic: prefers a `schema.org JobPosting` JSON-LD block, falling back to a Jev Choice only when JSON-LD is missing and regex-found candidates (`<title>`, `og:title`, `og:site_name`, first `<h1>`) are ambiguous — Jev always picks one candidate verbatim. Server-side fetching of arbitrary URLs goes through `src/lib/urlFetch.ts`, an SSRF-guarded fetcher: rejects non-http(s) schemes, resolves and rejects private/loopback/link-local IPs (re-checked after each manually-followed redirect hop, to avoid a validate-then-redirect bypass), ~10s timeout, ~2MB response cap.

## Key Patterns

**Server Actions** are the mutation layer — every create/update/delete is a `"use server"` function in an `actions.ts` colocated with its route. Pages are async RSC fetching directly via `prisma`; data-fetching pages export `dynamic = "force-dynamic"`.

**Ownership checks:** `Entry`, `Resume`, custom `Category`, and every tracker model (`Company`/`Application`/`Contact`/`Interaction`/`ApplicationContact`/`EmailThread`) have a required/nullable `userId`. Prisma's singular `update`/`delete`/`findUnique` build `where` from unique fields only — adding `userId` beside `id` does **not** enforce ownership. Always use `updateMany`/`deleteMany` with `{ id, userId }` and check the returned `count` (0 → `notFound()`), and `findFirst` (not `findUnique`) with `{ id, userId }` for reads. Built-in categories have `userId: null`; lookups including them use `where: { OR: [{ userId: null }, { userId }] }`. **The one exception** is `GmailAccount`, whose `userId` is itself `@unique` — `findUnique`/`update` keyed on `userId` alone is correct there; don't generalize it to any other model. The Phase 4 audit found a real miss in `confirmEmailThreadMatchForUser` (caller-supplied `contactId`/`applicationId` written without verifying ownership) — anything accepting a foreign id from client input must check it's owned by `userId`.

**Client-safe shared modules:** when a client component needs a server module's pure constants/types/CSV-or-matching logic (e.g. `APPLICATION_STATUSES`, a status-history formatter), put it in a `*Shared.ts` file with **no runtime import of `@/lib/prisma`** (only `import type` from `@prisma/client`) — see `applicationsShared.ts`, `interactionsShared.ts`, `notionImportShared.ts`. Importing the Prisma-touching file from a client component bundles the Prisma client into client JS. The non-Shared file stays server-only and re-exports its counterpart (`export * from "./xShared"`).

**shadcn/ui here uses `@base-ui/react`**, not Radix:
- `Button` has no `asChild` — use `buttonVariants` on a `<Link>`: `<Link className={cn(buttonVariants({ variant: "outline" }))}>`
- `Select.Value` renders the raw value string, not the item's label — render the label manually in the trigger
- `Checkbox` renders as `<button>`, not `<input>` — native `<label>` won't forward clicks; use a `<div onClick>` with `pointer-events-none` on the Checkbox
- `AlertDialog` doesn't use a Trigger here — manage `open` state manually

**Rich text in bullets/descriptions** is plain strings with `**bold**` and `*italic*` markers. `applyFormatting()` in `src/templates/jake.ts` converts them to `\textbf{}`/`\textit{}` after LaTeX-escaping; the preview parses them to `<strong>`/`<em>` in `EntryForm.tsx`.

**Entry field visibility** is driven by `src/lib/entryFields.ts`: `FIELD_CONFIGS` maps category slugs to `FieldConfig` objects controlling which fields `EntryForm` renders. Add a built-in category type by adding an entry; custom categories fall back to `DEFAULT_FIELD_CONFIG` (all fields).

**PDF compilation** is centralized in `compileResumeToPdf(templateId, identity, entriesByCategory)` (`src/lib/resumeCompiler.ts`) — the pdflatex/tempdir/cleanup mechanics (write `.tex`, run `pdflatex` twice with a timeout, read the PDF, clean up in `finally`) live there once. `GET /api/pdf/[resumeId]` (DB-backed, session-authenticated), `GET /api/pdf/snapshot/[snapshotId]` (snapshot-backed), and MCP `compile_resume` (inline, bearer-authenticated) each build `EntriesByCategory` differently and call it. Template-selection or pdflatex-invocation changes belong here, not in a route.

**Resume version history** (issue #26) fixes two gaps: `Entry` had no edit history, and `ResumeEntry` is a *live* FK, so editing an Entry retroactively changed every `Resume` and `Application` referencing it.
- **Entry history** — `updateEntryForUser` (`src/lib/entries.ts`) snapshots the pre-update field values into `EntryVersion.data` (JSON) before applying an edit, skipping no-op (deep-equal) saves. Audit-log only — no revert button. `EntryHistory.tsx` lists versions (collapsed by default) on the entry edit page, each expandable to its full field dump.
- **Resume pinning** — `attachResumeToApplication` (`src/app/(protected)/applications/resumeActions.ts`) calls `createResumeSnapshotForUser` (`src/lib/resumes.ts`), which freezes the resume's current rendered content (identity + inlined entry content grouped by category like the PDF route) into a new `ResumeSnapshot` and points `Application.resumeSnapshotId` at it. `Application.resumeId` is kept only for UI navigation (the picker in `ResumeSection.tsx` deals with the live `Resume`); the snapshot is what the application is pinned to and what "Download PDF" compiles. Later resume edits never change an attached application. No automatic re-sync: "Refresh snapshot" re-runs the attach flow to create a fresh snapshot. Applications attached before this feature have `resumeSnapshotId: null` and fall back to the live resume until re-attached.

**LaTeX template** lives entirely in `src/templates/jake.ts`: `escapeLatex` → `applyFormatting` → template string. Education uses `\resumeSubheading{school}{location}{degree}{date}` (location is arg #2, date arg #4), unlike Experience where date is arg #2.

**Do not edit the static LaTeX in `jake.ts`** (preamble, custom commands like `\resumeItem`/`\resumeSubheading`, margins, `\titleformat`) without a deliberate decision to diverge from upstream. It must stay byte-for-byte identical to the canonical template (https://github.com/jakegut/resume/blob/master/resume.tex — the "Jake Ryan" resume, credited in `jake.ts`'s header) except for one documented exception:

- `\usepackage[T1]{fontenc}` + `\usepackage[utf8]{inputenc}` — added in commit `ac0dc83` (2026-09-06). Upstream is a static ASCII example, but ResumePress renders arbitrary user Unicode (e.g. "José", "Renée"). Verified by testing: without them, modern pdfTeX doesn't crash, but accented characters render/extract as decomposed glyphs (e.g. "í" → "ı" + floating accent) — a visible defect.

Run `npm run check:jake-template` after any change to `jake.ts` — it renders the template with fixed dummy data and diffs against the golden fixture `src/templates/__fixtures__/jake.golden.tex`, failing with a line-level diff on any unintended change. If a static-LaTeX change is genuinely needed, update the golden fixture *and* add the discrepancy to the list above in the same commit.

**"Nord Paper" design system** — tokens in `globals.css` (Nord palette, `--radius: 0.125rem` for sharp corners, `--grid` for the dashed grid hairline, lifted further in dark mode so it stays visible). Headings use `font-heading` = Instrument Serif Italic, which has only a 400 weight; an unlayered `.font-heading` rule forces italic 400 so a stray `font-bold` can't produce faux bold. Page titles are `text-3xl tracking-tight font-heading`. `PageGrid` (`src/components/PageGrid.tsx`) is the **opt-in** page scaffold: a dashed four-column grid behind the page (`lg+` only), a header band, and the body; used by the dashboard and `/applications`. Opt-in because the lines only work on pages laid out on that grid — on a gridded page, every surface must be opaque (`bg-card`/`bg-background`) so lines stop at surfaces instead of running under text, and text sits `GRID_INSET` (24px at `lg`) inside its column. `PageHeader` puts its title and actions on opaque label boxes for the same reason. Statuses render as `StatusBadge` = `StatusDot` + label (tones in `applicationsShared.ts`; Rejected is a hollow ring so it never reads as Interviewing's amber). `SiteFooter` (protected layout) carries the daily-rotating colophon line.

**Card spacing gotcha:** the shadcn Card applies `py-(--card-spacing)` (16px) to itself plus `gap-(--card-spacing)` between children. For list-row cards using `CardContent` with its own `py-*`, add `py-0` to the `Card` to avoid double-stacking vertical padding.

## Data Model

```
User      id, name?, email?, image?  (+ NextAuth Account/Session/VerificationToken)
Category  id, name, slug, isBuiltIn, userId?  ← null = global built-in, set = a user's custom category
Entry     id, title, displayTitle?, organization?, location?, startDate?, endDate?,
          description?, bullets[], url?, tags[], categoryId, userId
          ← title is what renders into the PDF; displayTitle is a UI-only override with no PDF effect
EntryVersion  id, entryId, data (JSON snapshot of Entry's editable fields), userId, createdAt
          ← written by updateEntryForUser *before* applying an edit, so it only holds past versions; skipped on a no-op save
Resume    id, name, templateId ("jake"), identity (JSON), entries[], userId
ResumeEntry  resumeId, entryId, order  ← join table; order controls PDF ordering; entryId is a *live* FK — editing that Entry changes every Resume referencing it
ResumeSnapshot  id, resumeId? (SetNull), name, templateId, identity (JSON), entries (JSON, EntriesByCategory-shaped with entry content inlined, not FKs), userId, createdAt
          ← frozen copy of a Resume's rendered content, created by createResumeSnapshotForUser on each attach to an Application; self-contained, survives edits/deletion of the source Resume/Entries
ApiToken  id, name, tokenHash (unique), userId, lastUsedAt?, expiresAt?, revokedAt?  ← bearer tokens for MCP/agent auth

Company   id, name, website?, tier?, notes?, userId
Application  id, companyId, roleTitle, term?, status ("Applied" default, free-form),
          appliedAt?, postingUrl?, location?, source?, resumeId?, resumeSnapshotId?, notes?, externalId?, userId
          ← externalId is set by the Notion/CSV importer for idempotent re-imports; resumeId is for navigation/display, resumeSnapshotId is the actually-pinned frozen version (see "Resume version history")
ApplicationStatusHistory  id, applicationId, fromStatus?, toStatus, note?, changedAt, userId
          ← written on every Application.status change (same transaction); note-only rows (fromStatus === toStatus) are a user-authored "log update"
Contact   id, name, companyId?, title?, emails[], linkedinUrl?, phone?, howMet?, metAt?,
          notes?, tags[], nextFollowUpAt?, userId
ApplicationContact  applicationId, contactId, role (free-form), userId  ← composite @@id([applicationId, contactId])
Interaction  id, type (free-form), occurredAt, summary, contactId?, applicationId?,
          emailThreadId?, userId
          ← contactId/applicationId independently nullable; belongs to either, both, or neither
EmailThread  id, gmailThreadId, subject?, snippet?, participants[], lastMessageAt?, gmailUrl?,
          matchedContactId?, matchedApplicationId?, matchStatus ("unmatched" default: auto|confirmed|unmatched|ignored),
          jevRecruitingLikely?, jevRecruitingConfidence?, jevSuggestedContactId?, jevSuggestedContactConf?,
          jevSuggestedApplicationId?, jevSuggestedApplicationConf?, jevSuggestedNewCompany?, jevSuggestedNewRole?,
          jevSuggestedStatus?, jevSuggestedStatusConf?, jevClassifiedAt?, labelForced, userId
          ← @@unique([userId, gmailThreadId]); metadata/snippet only, never full bodies (jev* columns are suggestion-only, written by classifyThreadForTriage; labelForced is recomputed every sync from GmailAccount.syncLabelIds)
GmailAccount  id, userId (unique — see "Key Patterns" ownership exception), email,
          encryptedRefreshToken, scopes[], syncLabelIds[] (repurposed: holds the manual triage-override label id; the sync itself scans the whole inbox),
          historyId? (unused), lastSyncAt?, connectedAt, needsReauth,
          syncStatus ("idle" default: idle|running|error), syncStartedAt?, syncTotal?, syncDone?, syncError?
          ← the five sync* fields back the background-sync progress UI/polling
```

`identity` JSON shape: `{ name, email, phone, website, linkedin, github }`.

Built-in category slugs: `experience`, `education`, `projects`, `skills` — matched in `renderSection()` in `jake.ts` to pick the LaTeX render function.

## Adding a New Template

1. Create `src/templates/<name>.ts` exporting `render(identity, entriesByCategory)` with the same signature as `jake.ts`.
2. Register it in `TEMPLATE_RENDERERS` in `src/lib/resumeCompiler.ts`.
3. Add it to the `TEMPLATES` array in `src/app/(protected)/resumes/new/page.tsx`.
